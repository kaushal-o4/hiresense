# Deploying the HireSense demo (MongoDB Atlas + Render)

This puts a public demo online on free plans: the **database** on MongoDB Atlas, the **API and the web app** on
Render. The Blueprint `render.yaml` in the repository root creates both Render services at once. The hosted API uses
the *cloud profile*: Google Gemini answers the AI requests, the interviewer speaks with the browser's built-in voice,
spoken answers are transcribed by Gemini and job matching uses skills and keywords. The local models (Ollama,
Whisper, Kokoro, sentence embeddings) need a GPU laptop and are not used here.

```
browser ──► https://<web>.onrender.com            (nginx: React build, forwards /api/*)
               └─ /api/*  ──proxy──► https://<api>.onrender.com/api/*   (FastAPI, Docker)
                                            ├─► MongoDB Atlas (M0)
                                            └─► Gemini API (Google)
```

The browser only ever talks to the web app's domain, so the login cookie is first-party (`SameSite=Lax`).
If you prefer Vercel for the web app (its `/api` rewrite plays the same role as nginx), that still works —
see section 5.

| Account / value | Where | Cost |
|---|---|---|

| Render account (sign in with GitHub) | https://render.com | two free web services |
| Gemini API key | https://aistudio.google.com/apikey | free tier with rate limits; paid beyond it |
| Vercel account (optional, alternative web host) | https://vercel.com | free Hobby plan |
| A strong admin password | you choose | |

## 1. Database: MongoDB Atlas

1. Create a project, then **Build a database → M0 (Free)**. Pick a region near Render's (AWS Mumbai or Singapore).
2. **Database Access → Add new database user**: username `hiresense`, a generated password, role
   *Read and write to any database*.
3. **Network Access → Add IP address → Allow access from anywhere (`0.0.0.0/0`)**. Render's free plan has no fixed
   outgoing IP, so the user/password is the protection. Use a long generated password.
4. **Database → Connect → Drivers** and copy the connection string, e.g.
   `mongodb+srv://hiresense:<password>@cluster0.abcd1.mongodb.net/?retryWrites=true&w=majority`.
   Put the real password in (URL-encode `@ : / ? #` if it has any).

## 2. Gemini key

Create a key in Google AI Studio. Set a budget/quota alert in Google Cloud if billing is on: every interview turn,
resume analysis and spoken answer is a request. The demo caps each user at `AI_DAILY_LIMIT_PER_USER=60` AI calls a day.

## 3. API and web app: Render (Blueprint)

1. Push the repository to GitHub.
2. Render → **New → Blueprint** → choose the repository (branch `main`). Render reads `render.yaml` and creates two
   Docker services, `hiresense-api` (FastAPI) and `hiresense-web` (nginx), both on the free plan in Singapore. It
   asks for three values:
   - `MONGODB_URL`: the Atlas string from step 1
   - `GEMINI_API_KEY`: from step 2
   - `ADMIN_PASSWORD`: the first admin's password (login `admin@hiresense.app`)
   Leave `REDIS_URL` empty (one instance). `SECRET_KEY` is generated by Render.
3. **Service names on Render must be free.** If `hiresense-api`/`hiresense-web` are taken, Render appends a suffix
   (`hiresense-api-a1b2.onrender.com`) and two cross-links break until you fix them (Render → service →
   **Environment**):
   - on `hiresense-web`: `API_UPSTREAM` = the real API host (e.g. `hiresense-api-a1b2.onrender.com`)
   - on `hiresense-api`: `FRONTEND_URL` and `CORS_ORIGINS` = the real web address (`https://hiresense-web-a1b2.onrender.com`)
   With the default names (`hiresense-api.onrender.com`, `hiresense-web.onrender.com`) the Blueprint values are
   already correct and you can skip this.
4. Wait for both deploys, then check:
   - `https://<api>.onrender.com/api/health/ready` → expect `"database": {"ok": true}`, `"language_model": {"ok": true}`,
     and `speech_synthesis`/`embeddings` listed as degraded (those two are off on purpose in the cloud profile).
   - `https://<web>.onrender.com/` → the HireSense login page; signing in works without any extra CORS setup,
     because nginx forwards `/api/*` to the API (the API only sees same-site requests).
5. Each API start runs `python -m app.seed_initial_data` (safe to repeat): it creates the admin account, badges and
   the question bank.

## 4. Check it

1. Open the web app URL and sign in as `admin@hiresense.app`. Change the password in Account settings if you used a
   temporary one.
2. Register a student. The register form shows the optional "processed by Google Gemini" checkbox. Leave it
   unticked: the interview page must show the AI data notice, and starting an interview must be refused until you
   click **I agree**.
3. Start a **live voice interview** in Chrome or Edge. The interviewer speaks with the browser voice. Answer out
   loud: the text appears after each pause. There are no live word-by-word captions with Gemini speech recognition.
4. Check `/privacy`.

## 5. Alternative: web app on Vercel

If you already host the API on Render and want the web app on Vercel instead (its `/api` rewrite replaces the nginx
proxy, with the same first-party-cookie behaviour):

1. Edit `frontend/vercel.json` and replace `REPLACE-WITH-YOUR-API.onrender.com` with the Render API host. Commit and push.
2. Vercel → **Add New → Project** → import the repository → **Root Directory: `frontend`**. The framework preset is
   Vite. No environment variables are needed. Deploy.
3. On Render, change the API's `FRONTEND_URL` and `CORS_ORIGINS` to the `https://<project>.vercel.app` address and
   redeploy. (In the Blueprint they point at the Render web app; the cross-site-write protection in the API checks
   these two values against the browser's `Origin` header.)

## Option B: frontend calls the API domain directly

Use this if the /api proxy or rewrite gives you trouble. In this option the browser sends the cookie to
`onrender.com` itself:

- Build the frontend with `VITE_API_URL=https://<api>.onrender.com` (on Vercel: an environment variable; in the
  nginx image: the `VITE_API_URL` build arg) and remove the `/api` rewrite from `vercel.json` if you host there.
- On Render: set `COOKIE_SAMESITE=none` (Secure is forced on) and keep `CORS_ORIGINS` at the frontend's address.

Browsers that block third-party cookies (Safari, and Chrome with that setting on) will then not keep the login.
That is why the proxy through the frontend's own domain is the default.

## Option C: one server with Docker

```
cp .env.docker.example .env.docker     # fill in MONGO_PASSWORD, SECRET_KEY, GEMINI_API_KEY, ADMIN_PASSWORD
docker compose --env-file .env.docker up -d --build
```

This starts MongoDB (with a password, not exposed to the host), the API and nginx on `http://localhost:8080`. Put an
HTTPS reverse proxy (Caddy, Traefik, a cloud load balancer) in front and set `COOKIE_SECURE=true` and
`FRONTEND_URL=https://your-domain`.

## Known limits of the free demo

- **Cold starts:** a free Render service sleeps after 15 minutes idle. The first request then takes about a minute —
  on both services, so the first page load after an idle night can take over a minute. Reload rather than giving up.
- **Uploaded resume files** live on the Render instance's temporary disk and are lost on restart or redeploy. The
  extracted text and the analysis stay in MongoDB, so the app keeps working, but "Download resume" fails for older
  uploads. Attach a Render disk at `/data` and set `UPLOAD_DIR=/data/uploads` to keep them.
- **One instance:** login lockout and rate limits are in memory unless `REDIS_URL` is set. Set it before running more
  than one instance.
- **Atlas M0:** 512 MB storage and shared CPU. Fine for a demo, not for a whole college.
- **Unverified on the real services yet:** streamed interviewer replies (Server-Sent Events) pass through nginx with
  buffering off, which is the supported setup, but try one live interview and one resume upload right after the
  first deploy anyway.
